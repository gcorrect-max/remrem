REM102 – CGI API (read-only)

Description of the HTTP requests that the REM102 web interface uses to fetch data. Compiled from home.json, setup.json, advanced.json, monitoring.json and settings.json. Only read requests are included.

Status. The scripts/rem102-info.sh script was tested against a mock server, not a real device. The response body format and the login parameters are assumptions – see Assumptions.
Base URL
http://<HOST>        # default 192.168.128.1

The device exposes four CGI files:

CGI fileScope
/cgi-bin/mpc105.fcgiplatform: login, networking, GPS, modem, RTC, device information, memories
/cgi-bin/rem.fcgiREM meter: status, EMF channels, DCS, Digital IO, channel configuration
/cgi-bin/items.fcgiDMeter (iTEMS)
/cgi-bin/rtp.fcgiRTP100

Login

POST/cgi-bin/mpc105.fcgi
curl -c "$JAR" -X POST "http://$HOST/cgi-bin/mpc105.fcgi" \
     --data-raw "query=120&username=Admin&pwd=PASSWORD"

After a successful login the device sets the CGIUSERNAME and CGIUSERLEVEL cookies. Send every further request with -b "$JAR".

queryFunction
query=120login
query=125authentication message (identity.auth_message)
query=126hostname (identity.host)
query=121change password – a write, not used
query=1983logout

Pages with show_level 1 or 2 may require an account with a higher level (CGIUSERLEVEL).

Conventions

  • Read requests are sent with GET: curl -G … --data-raw "query=…" appends the parameters to the URL.
  • In the menu files the query field sometimes separates parameters with ~ (e.g. query=450~user=1). In the real request this is &: query=450&user=1.
  • The en_cgi/en_query menu fields check whether a module is enabled – these are the packages in the Features tab.
  • The set and set1 fields write configuration – they are not used.

Response format

The script returns one JSON object: device + a key per tab + packages keyed by id.

{
  "device": { "host": "192.168.128.1", "collected_at": "2026-10-16T22:32:11Z" },
  "identity": {
    "device_settings": {
      "label": "Advanced > Information > Device Settings (model, serial no., article no.)",
      "cgi": "/cgi-bin/mpc105.fcgi",
      "query": "query=302",
      "http_status": 200,
      "body": { "…": "device response" }
    }
  }
}
FieldDescription
labelpath in the web menu
cgi, queryexactly what was sent to the device
http_statusHTTP code; 0 = connection error or timeout
bodyJSON if the response parses; otherwise raw text; null when empty

A failure of one package (e.g. a disabled module) does not stop the collection of the others.

rem.fcgi?query=402Export SIC Configuration – an export action
mpc105.fcgi?query=122Accounts Management – user account data
items.fcgi?query=410, rtp.fcgi?query=442/443/445DMeter and RTP100 writes/commands
all set / set1 fieldsconfiguration writes

Script

REM_HOST=192.168.128.1 REM_USER=Admin REM_PASS='…' ./scripts/rem102-info.sh > rem102.json

# additionally one JSON file per package: ./dump/<tab>/<id>.json and ./dump/all.json
REM_OUT_DIR=./dump REM_HOST=… REM_USER=… REM_PASS=… ./scripts/rem102-info.sh > /dev/null
VariableMeaningDefault
REM_HOSTdevice address (may include a port)192.168.128.1
REM_USERloginrequired
REM_PASSpasswordrequired
REM_LOGIN_BODYfull login request bodyquery=120&username=…&pwd=…
REM_OUT_DIRdirectory for separate package filesdisabled

Requires bash, curl, jq. jq examples:

# device identification
jq '.identity | {device_settings: .device_settings.body, version: .version.body}' rem102.json

# packages that failed
jq -r 'del(.device) | to_entries[] | .key as $t | .value | to_entries[]
       | select(.value.http_status != 200) | "\($t)/\(.key): HTTP \(.value.http_status)"' rem102.json

LabVIEW integration

The request list is available as files in data/rem102/, ready to load in LabVIEW. Row order is identical in all files.

FileContentUse
rem102-package-names.txtone package name per line (tab.id)enum items (typedef)
rem102-package-requests.txtone request per line: /cgi-bin/mpc105.fcgi?query=302string array indexed by the enum value
rem102-packages.tsvall columns with a header: index, name, tab, id, cgi, query, request, method, min_level, requires, labellookup by name, gating on min_level and requires

Names are tab.id because a bare id repeats (e.g. gps exists in Setup, Monitoring and Features).

Flow

  1. Enum. Create a typedef REM102 Package with the items from rem102-package-names.txt. The enum value is the 0-based line number.
  2. Request array. Read from Text File (with end-of-line conversion), split into lines into a String[]. Load it once at start-up (functional global or DVR).
  3. Request. Index Array with the enum value → path. Prepend http:// + host.
  4. GET. HTTP Client with the session cookies from login (query=120) → response body as a string.
  5. Parsing. Unflatten From JSON into the typedef of that package.

Polymorphic VI

A polymorphic VI picks its instance by the type of the wired data, not by an enum value. So the enum selects the request and the type selects the parser. For a single VI that handles every package, a malleable VI (.vim, LabVIEW 2017 or newer) fits best:

Get Package.vim
  inputs:   Package (enum REM102 Package), Type (any typedef – type specifier), Host, session
  outputs:  Data (of type Type), Raw Body (string), HTTP Status, error out
  inside:   Index Array(requests, Package) → HTTP GET → Unflatten From JSON(Type)

Each package only needs its own cluster typedef – no separate instance. A classic polymorphic .vi also works but needs one instance per typedef.

Until you know the real responses, use a Get Package (Raw).vi that returns just the string. Build the typedefs from samples collected with the script (REM_OUT_DIR) on a real device.

Before reading, check the min_level (account level) and requires columns in the tsv (the features.* package that tells whether the module is enabled).

Assumptions

  1. Login. The menu files give only query=120. The username and pwd field names and the cookie names come from the LabVIEW configuration (data/modulesCfg.ts). If login fails, capture the real request in DevTools and pass it in REM_LOGIN_BODY.
  2. GET vs POST. Reads use GET. If responses are empty, try POST.
  3. Response format. It is not known whether the device answers with JSON. The script handles both JSON and plain text.
  4. Access levels. show_level is taken to mean the minimum user level needed to display the page.
